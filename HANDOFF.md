## Security and database cautions

- **Never run tests against `DATABASE_URL` or production `public`.** Tests must only ever use `TEST_DATABASE_URL` → `pitchpilot_test_runner` → `pitchpilot_test` schema.
- **Never use `DROP SCHEMA`, `CASCADE`, or broad cleanup against production.** Test cleanup (`Base.metadata.drop_all()`) is scoped to `pitchpilot_test` only via `schema_translate_map`; it is never applied to `public`.
- ⚠️ **The Supabase Data API "Exposed Schemas" setting has not been independently confirmed.** A prior audit found `public.leads` had RLS disabled and broad `anon`/`authenticated`/`service_role` SQL grants (now fixed by enabling RLS — see above), but whether `public` is actually reachable over Supabase's REST API depends on a project-level dashboard setting (Settings → API → Exposed Schemas) that cannot be checked via SQL. This was never independently verified — it was assumed to still be at Supabase's default (which typically exposes `public`). The RLS fix mitigates the data-access risk regardless of this setting, since RLS with zero policies denies all non-owner access either way.
- **RLS is enabled on `public.leads` with zero policies.** This is intentionally minimal — it denies all access to non-owner roles (`anon`, `authenticated`, `service_role`) by default, without needing to define any policy. Do not casually add RLS policies, change the existing grants, enable `FORCE ROW LEVEL SECURITY`, or change Supabase API settings without a separate, explicit review — each of those has different blast-radius implications that haven't been evaluated.
- **The backend connects as `postgres`, the table owner, which bypasses RLS by default** (confirmed via a live INSERT/SELECT sanity check after the RLS migration was applied, in the prior session). This means RLS currently protects against the Data API / other non-`postgres` connections, but does **not** provide any application-level authorization — the FastAPI backend's own endpoints have no auth/authorization layer at all yet. Do not treat RLS as a substitute for that.
- **Never include credentials or secrets in documentation, commit messages, or chat.** Refer to environment variable names only (`DATABASE_URL`, `TEST_DATABASE_URL`, `BACKEND_CORS_ORIGINS`, `NEXT_PUBLIC_API_BASE_URL`) — never their values. This document contains none.

## Fix for the Checkpoint 3 RLS/commit bug (2026-10-18)

The blocking issue found by the 2026-10-17 security review (item 3 below) is fixed and verified. No migrations executed, no roles/grants/production settings/data touched, no secrets printed. Nothing staged, committed, or pushed. Several temporary diagnostic test files were used to trace the exact SQL SQLAlchemy was generating and were deleted immediately after; they are not part of the permanent suite.

**Root cause, precisely:** `set_rls_user_context` sets `app.current_user_id` via `set_config(..., true)` — transaction-scoped by design (see `DECISIONS.md`). `create_lead`/`update_lead`/`archive_lead` each called `db.commit()` (ending that transaction, clearing the GUC) followed by `db.refresh(lead)` (a fresh `SELECT` in a new transaction, where the GUC had reverted to `''` and the RLS policy's `::uuid` cast raised `DataError`). Removing just the explicit `refresh()` would not have been enough: SQLAlchemy's default `expire_on_commit=True` would have triggered the same class of implicit lazy-reload query the moment FastAPI/Pydantic read any attribute off the committed object to build the response — and, separately, `updated_at` (a server-side `onupdate=func.now()` column) turned out to need its own explicit opt-in to be fetched eagerly via `RETURNING` on `UPDATE` specifically (confirmed by reading SQLAlchemy's own source — `orm/persistence.py`'s `_collect_update_commands` only takes the eager/RETURNING path for UPDATE when `mapper.eager_defaults is True`, not the library's "auto" default, which only covers INSERT).

**The fix, three small pieces, all targeting the actual root cause (no GUC re-setting anywhere):**
1. `app/database.py`'s `get_db()` — session factory now sets `expire_on_commit=False`, and wraps the yield in `except Exception: db.rollback(); raise` before the existing `finally: db.close()` (explicit, not just relying on `close()`'s implicit rollback).
2. `app/models/lead.py` — `updated_at` gained `server_onupdate=FetchedValue()` (tells the ORM this column is server-onupdate-managed and should be fetched via `RETURNING`), and the `Lead` mapper gained `__mapper_args__ = {"eager_defaults": True}` (the piece that actually turns on `RETURNING` for `UPDATE`, not just `INSERT`).
3. `app/api/v1/leads.py` — removed the three now-unnecessary (and previously bug-causing) `db.refresh(lead)` calls in `create_lead`/`update_lead`/`archive_lead`. `created_at`/`updated_at` are now populated by `RETURNING` during the flush `commit()` already performs, *before* the transaction (and the RLS GUC) ends — nothing in these routes queries the database again after a commit.

Full design reasoning — why this beats "just re-call `set_rls_user_context` after commit," and why `app/core/sessions.py`'s identical-looking `db.commit(); db.refresh()` pattern was deliberately left alone — is in `DECISIONS.md`'s "Mutating routes read server-generated columns from the same transaction that writes them" entry.

**New regression tests (`backend/tests/test_rls_commit_regression.py`, 6 tests), deliberately NOT using the existing `db_session`/`client` fixtures** (which bind the Session to an already-open external transaction, making `db.commit()` a no-op at the database level — the exact reason the original Checkpoint 3 suite passed 44/44 while this bug was present). Instead, a new `production_like_client` fixture monkeypatches `app.database.get_engine` to point at the restricted `pitchpilot_test_app` engine and lets the real, unmodified `get_db()`/`get_current_user()`/route code run through real HTTP-shaped requests (register → login → mutate) — a session bound directly to the Engine, with no externally pre-opened transaction, exactly matching production:
- `test_create_lead_succeeds_with_real_commit_and_rls` / `test_update_lead_succeeds_with_real_commit_and_rls` / `test_archive_lead_succeeds_with_real_commit_and_rls` — each of the three previously-broken routes, now passing with a real commit and the real RLS policy enforcing.
- `test_cross_user_isolation_holds_with_real_commit_and_rls` — two independently registered users under this same real-commit lifecycle; user B gets 404 on user A's lead via GET/PATCH/DELETE, user A still gets 200 on their own lead with data unaffected by the rejected attempt.
- `test_failed_update_leaves_no_committed_change` — a PATCH to a nonexistent lead_id returns 404, and a direct admin-role (RLS-bypassing, ground-truth) query confirms no row with the attempted data was ever committed anywhere; the real lead's original data is confirmed unchanged.

## Authentication — Checkpoint 3 of 6 (database roles, RLS policies, transaction-scoped user context)

**Unresolved risks, explicitly carried forward (not fixed this checkpoint, by design/scope):**
1. **The GUC-forgery limitation is real in production too, not just a test artifact.** If the production `pitchpilot_app` role is ever granted broader permissions, or if a future SQL injection vulnerability gives an attacker arbitrary SQL execution as that role, RLS via this GUC provides **no protection** — the attacker can simply set the GUC to any user's id. This design's actual, verified value is catching *application code mistakes*, not malicious SQL execution.
2. **`users` and `sessions` are not RLS-protected.** Only `leads` has an owner column and policy. A bug in a future `users`/`sessions` query with no `WHERE` clause has no database-level backstop.
3. **No production role or policy exists yet.** `pitchpilot_app` is not created; migration `b2b5b3f0c716` is authored for review only. Even once applied, it has zero effect until the app's production DB connection switches away from the owning `postgres` role — that switch is a separate, not-yet-scoped future step with its own blast radius (every production query starts going through a non-owner role).
4. **The `''`-not-`NULL` `current_setting` behavior should inform any future RLS policy.** Any new RLS policy on a different table that reads this or a similar GUC should account for the empty-string case explicitly (e.g. via `nullif(current_setting(...), '')`) if "silently deny with zero rows" is preferred over "loudly error" for that table's failure mode — this checkpoint deliberately left `leads` erroring loud, but that was a discovered behavior, not a chosen one, and wasn't re-evaluated against product requirements for every table.
